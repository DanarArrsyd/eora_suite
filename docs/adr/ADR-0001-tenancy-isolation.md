# ADR-0001 — Multi-tenancy and tenant isolation

- **Status:** Accepted (D-009, DD-07) · **Date:** 2026-10-08 · **Amendment 1** (2026-10-09, D-053): policy expression and role split · **Amendment 2** (2026-10-11, D-055/D-056): signed tenant context replaces the GUC predicate — see end of document

## Context
EORA is multi-tenant SaaS holding manufacturing stock, customer demand and quality data. A leak between tenants is a critical incident. Options considered: (a) shared DB + `tenant_id`, (b) schema per tenant, (c) database per tenant. Expected scale (D-019): tens of tenants initially, growth expected; one ledger design must serve all.

## Decision
1. **Shared PostgreSQL database**, single schema per bounded context namespace (table prefixes or PostgreSQL schemas per module — chosen at Foundation, not per tenant).
2. Every tenant-owned table has `tenant_id uuid NOT NULL`. Primary key `id` (UUIDv7/ULID) plus `UNIQUE (tenant_id, id)`. **All foreign keys between tenant-owned tables are composite** `(tenant_id, x_id) REFERENCES x (tenant_id, id)`, so a row can never point to another tenant's row even if application code is wrong.
3. Unique business keys are tenant-scoped, e.g. `UNIQUE (tenant_id, doc_type, doc_no)`.
4. **Layer 1 — application:** tenant resolved from authenticated session membership (DD-07), never from a client header or URL. Eloquent global scope adds `tenant_id`; repository/query classes require a `TenantContext` value object; authorization policies check tenant + plant/warehouse scope (doc 05).
5. **Layer 2 — RLS (defense-in-depth):** `ALTER TABLE … ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY` on tenant tables; policy `USING (tenant_id = (SELECT c.tenant FROM ctx_api.context() c)) WITH CHECK (same)` (Amendment 2; the Amendment 1 GUC expression is now only the documented rollback body). The application DB role is **not** owner and has no `BYPASSRLS`. Migrations run under a separate owner role.
6. **Tenant context propagation rule (pooling-safe):** *(superseded in its mechanism by Amendment 2: the context is a signed, transaction-bound token in `app.ctx`; the transaction-local, fail-closed principle below is unchanged)* tenant context is set with `SELECT set_config('app.tenant_id', $1, true)` — i.e. `SET LOCAL` semantics — **inside a transaction**. All tenant DB work (reads included) executes inside a transaction opened by a `TenantTransaction` middleware/unit-of-work. If `app.tenant_id` is unset **or reset**, RLS policies match nothing (fail closed: `NULLIF(current_setting('app.tenant_id', true), '')` is NULL → no rows; Amendment 1). This remains correct under PgBouncer transaction pooling and under persistent PHP workers.
7. **Workers/queues:** every job payload carries `tenant_id` and the initiating `user_id` (or `system` actor). A job middleware establishes TenantContext and opens the tenant transaction; jobs without tenant context throw before touching tenant tables. Platform-level jobs (tenant provisioning, metrics) use explicit, audited platform services that never read operational tables.
8. **Other channels:** object-storage keys prefixed `tenants/{tenant_id}/…`; cache keys prefixed `t:{tenant_id}:`, plus permission scope hash where results are permission-dependent; Reverb private channels `tenant.{tenant_id}.user.{user_id}` authorized server-side; outbox, inbox, import/export jobs and logs all carry `tenant_id`.
9. Hierarchy: `tenant` = customer account; `company` = legal entity inside tenant; `plant` → `warehouse` → `location`. V1 pilot: one company, one plant active per tenant; schema supports many.

## Consequences
+ One schema to migrate; cross-tenant platform ops simple; strong DB-level backstop.
− Every query/index needs `tenant_id` as leading column; noisy-neighbour risk handled by rate limits and later sharding by tenant if needed.
− Requests run inside transactions (including reads) — keep them short; no external I/O inside.

## Verification (mandatory automated tests)
- T-ISO-01: Tenant A user requests Tenant B record by ID via API, export, report, file URL, notification deep link, search, websocket channel → 404/403, no data, audit event.
- T-ISO-02: RLS backstop — raw query with application role and tenant A context cannot read/write tenant B rows, including via composite FK insert attempts.
- T-ISO-03: Pooling leak — interleave requests of tenants A/B over a transaction-mode pooler and persistent workers; assert zero cross reads; assert unset context returns zero rows.
- T-ISO-04: Queue job for tenant A processed after job for tenant B on the same worker process never sees B context.
- T-ISO-05: Cache/permission-scope keys differ per tenant and per scope; export file paths unguessable and tenant-prefixed.

## Amendment 1 — RLS policy expression and role separation (2026-10-09, D-053)
**Status:** recorded with the B1 architecture review (doc 25); implementation follows B1 approval.
1. **Reset context is an empty string, not NULL.** After a connection has used `set_config('app.tenant_id', …, true)`, the setting reverts to `''` at transaction end (verified on PostgreSQL 18.6). `current_setting('app.tenant_id', true)::uuid` then raises `invalid input syntax for type uuid` on any reused or pooled connection. Every policy therefore uses
   `tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)` for `USING` and `WITH CHECK`; the `(SELECT …)` wrapper evaluates the setting once per statement. Unset and reset contexts both fail closed (no rows); a malformed value still errors (never widens).
2. **Roles:** bootstrap superuser (role/database creation only), `eora_owner` (DDL, migrations), `eora_auth_definer` (NOLOGIN, owns the `auth` schema + reviewed `SECURITY DEFINER` functions), `eora_app` (business runtime; NOSUPERUSER, NOBYPASSRLS, owns nothing, **no privilege on `auth`/`auth_api`**), `eora_auth_web` (login, reset/invitation consumption — cannot issue secrets), `eora_auth_delivery` (separate worker; issues invitation/reset secrets — cannot consume them), `eora_provisioner` (member of `eora_app` + tenant creation; NOBYPASSRLS); `eora_prov_definer` (NOLOGIN, owns the provisioning registry `prov`/`prov_api`); `eora_outbox_definer` (NOLOGIN) + `eora_relay` (LOGIN, EXECUTE only) for the global outbox claim, so the runtime role needs no global read (doc 25 §6.4); `eora_ctx_verifier` (NOLOGIN, owns `ctx`/`ctx_api` for the signed tenant context — approved, Amendment 2). `security_events` and `outbox_events` carry a `source` column; the runtime role may write only `source = 'app'`. Platform tables `tenants` and `memberships` use forced RLS with the context-aware policies of doc 25 §2.6; login identity and credentials live in `auth.identities`, reachable only through definer functions (doc 25 §2.1–§2.4). Denied-access security events are written after the request transaction ends (doc 25 §8).
3. **Threat-model limit:** `app.*` settings can be set by any session, so context-based RLS contains application bugs (missing filters, unscoped jobs) — not an attacker able to execute arbitrary SQL as the runtime role. No authentication or ownership decision may rely on these settings; SQL-injection defence relies on parameterized statements (native prepares), static checks and the role boundaries above; a signed tenant context (separate `ctx`/`ctx_api` schemas, HMAC bound to backend pid and transaction start) was **preferred for a security PoC** (doc 25 §5.5, D-B1-24) → **approved 2026-10-11, see Amendment 2**.
4. **Verification additions:** isolation, authorization and privilege tests run as the non-superuser runtime roles (never superuser/owner) and assert it at bootstrap; T-ISO-02b (unset, reset and malformed context), T-PROV, T-CTX, T-LOGIN, T-INV, T-RST and T-SEV suites (doc 25 §12). T-ISO-01's audit event is the durable `security_events` row.

## Amendment 2 — Signed tenant context (2026-10-11, D-055, D-056)
**Status:** Accepted (owner approved D-B1-24 Option 1 after the security PoC and its optimization phase). Implementation is part of milestone M1 (B1) and needs the M1 scope approval (D-054).
1. **Mechanism.** Within the tenant transaction the application sends `BEGIN` together with the binding read (`pg_backend_pid()`, transaction start in µs) as one constant simple-protocol statement, signs `v1.<kid>.<tenant>.<actor>.<pid>.<xact_us>.<exp>` with HMAC-SHA256, and sets it with the bound parameter `set_config('app.ctx', $1, true)`. The token itself is never interpolated into SQL text.
2. **Verifier.** `ctx_api.context()` returns `(tenant uuid, actor uuid)`. It is owned by NOLOGIN `eora_ctx_verifier`, `SECURITY DEFINER`, `STABLE`, **`PARALLEL RESTRICTED`** (D-056 P-01), has no arguments and `SET search_path = ''`. It checks shape → active key by `kid` → HMAC over the raw payload → only then parses → pid, transaction start and `exp`. Any failure returns NULLs. Keys live in `ctx.keys`, which no login role can reach.
3. **Policies.** `tenant_id = (SELECT c.tenant FROM ctx_api.context() c)`. Actor-bound checks use `(tenant_id, actor) = (SELECT c.tenant, c.actor FROM ctx_api.context() c)`. A tenant-less token (tenant picker before a tenant is chosen) yields tenant NULL and the actor, which satisfies doc 25 §2.6 P2 only. Replay in another transaction or backend yields NULL.
4. **Privileges and hardening.** The table-owning role gets `USAGE` (no `EXECUTE`) on `ctx_api` (P-02). Runtime roles set `log_parameter_max_length = 0` and `log_parameter_max_length_on_error = 0` (P-03). CI asserts the exact `SECURITY DEFINER` allowlist (P-04). Native prepared statements through PgBouncer require libpq ≥ 17 (installed from apt.postgresql.org on the bookworm base, P-05). Database role passwords are never sent as plaintext through statements tracked by `pg_stat_statements` (P-06).
5. **Performance budget** (replaces the PoC's p95 < 2 % target): ≤ 0.3 ms p95 per transaction and ≤ 15 µs per RLS table reference at the database level, enforced by a CI regression benchmark. PoC measurement: +0.16–0.27 ms p95 on W-01/W-02.
6. **Threat model.** Arbitrary SQL as the runtime role can no longer forge another tenant's or actor's context. It can still act within the current tenant (inherent), so the Amendment 1 point 3 defences remain: parameterized statements, static checks and role boundaries. Out of scope: compromise of the PHP process or its secrets, and compromise of the superuser or owner role. The key is also present in database backups, so backup access is treated as key access.
7. **Rollback.** Replacing the body of `ctx_api.context()` with Amendment 1 GUC semantics is a single migration, rehearsed in PoC-CTX-12. It runs only by explicit owner decision, never automatically.
8. **Verification.** T-CTX suite = PoC-CTX-01..14 + 05b ported to the B1 test groups (doc 25 §11), plus the definer allowlist and the performance gate.
