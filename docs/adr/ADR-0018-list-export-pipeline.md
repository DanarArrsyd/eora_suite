# ADR-0018 — List export pipeline: queued job, same QueryDefinition, signed short-lived link

- **Status:** Accepted (D-092) · **Date:** 2026-10-27

## Context
M2 step 7 (doc 29 §1.7, §4 item 5) needs master lists exported "through the same query" as the screen. Doc 08 §Secure
export asks for server-side scope and identical filters, a query snapshot, a queue for large jobs, an expiring signed
download, storage cleanup, audit, notification and formula-injection escaping; doc 24 §3 already names an async export
job. The owner fixed the rules in D-092: always a queued job, a 15-minute link, a file kept 24 hours, at most 100,000
rows, every list column with the screen's headings.

## Decision
1. **One SQL for list and export.** `QueryRunner::build()` returns a `BuiltQuery` (FROM/WHERE, order, bindings); the list
   page, the EXPLAIN checks (ADR-0008, D-093) and the export read it. A list is exportable when its QueryDefinition
   declares `exportColumns()` (`ExportColumn`: heading, field or computed value, type, enum labels) and a `title()`.
2. **Job.** `POST /api/v1/exchange/exports {resource, filter, q, sort}` needs `exchange.export.export` and the list's view
   permission, counts the rows (422 above the limit) and queues `ProcessExport` on the Redis queue `exports` (served by the
   `import-worker` service). The job row (`export_jobs`) keeps the list request; RLS shows a job to its requester only
   (the file holds what that person may see) and to the system actor that expires files.
3. **Worker.** As the requester, in one tenant transaction: build again (permissions and scopes as of now; a lost role
   fails the job `NOT_ALLOWED`), fix the matching ids in list order with one statement (one snapshot; a list that grew
   past the limit fails `TOO_MANY_ROWS`), read the rows by id in chunks of 1,000 with the full FROM, stream them into the
   workbook (OpenSpout, ADR-0017), store it on the `exports` disk (same private bucket, `tenant/<id>/exports/<job>/`),
   mark the job DONE with its expiry and notify the requester in the inbox (deep link `/system/exports?job=<id>`).
4. **Workbook.** Data sheet named after the list: bold headings, frozen heading row, auto-filter, typed cells (numbers,
   dates, date-times in the tenant's time zone, Yes/No, screen labels for enums); a screen cell showing several facts
   becomes one column per fact; text that would start a formula gets an apostrophe. About sheet: list, rows, search,
   filters, sort, data as-of with the time zone, requester and the footer `Generated by EORA Suite | Exported on …`.
5. **Download.** `POST /exchange/exports/{job}/link` issues a relative signed URL valid 15 minutes (audited);
   `GET /exchange/exports/{job}/file` needs the valid signature **and** the requester's session (tenant middleware + RLS),
   so a leaked link alone opens nothing.
6. **Cleanup.** `eora:exports:expire` (hourly, new `scheduler` service with the provisioner credential only) deletes files
   past 24 hours and marks the jobs EXPIRED; links already refuse an expired job, so a late run never extends access.

## Consequences
- Exports cannot drift from the list: a new list column needs its export column in the same QueryDefinition, and a test
  checks every export column reads a field the definition has.
- Row values are read just after the id snapshot, so a value edited during a long export may be newer than the as-of
  time; the set of rows and their order are fixed. Master data is never hard-deleted, so no row disappears.
- PDF export waits for O-010 (branding/print templates).

## Verification
`tests/Feature/Export/ExportTest.php`: exportable lists and their columns, filter/search/sort replayed, typed cells,
formula escaping, About sheet, inbox notification and audit, signed link (tampered and 16-minute-old links refused,
another member gets 404), 24-hour expiry, row limit up front and at run time, plant scope, permission lost before the
run, routings with their shown-only laterals. Live: real worker and SeaweedFS, file downloaded through the link.
